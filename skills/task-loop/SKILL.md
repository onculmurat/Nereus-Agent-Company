# Task loop

Adapted from superpowers subagent-driven development (see NOTICE).

The board (`team/work/board.md`) is the source of truth. A task whose board status is `done` is never dispatched again, even if you do not remember finishing it.

## For each board entry that is not `done`

1. **Brief.** Make sure the task has a brief (written by the planner). It names files, interfaces, exact values, the failing tests to write first and the commit message.
2. **Start.** `node "<scripts>/task.js" start <id> --role <owner-role>` (add `--worktree` when another code task is in progress; `--paths <p1,p2>` for the pack). One call does the bookkeeping (g33): board `in-progress` (with the same refusals as `board.js update`), the hand-off skeleton `team/work/handoffs/<id>.md` with the base commit read from git, the worktree when asked, the role's context pack (step 3) and one `chore(team): <id> start` commit. Use the printed `base` as the task's base; never write it from memory. If the brief cites threat-model IDs, the task is tagged `security: yes` and the output says so (`securityNote`); change it to `contract` (`board.js update <id> --security contract`) when the task changes a security contract. During the task, add what the next session needs (gate result, review verdict, decisions, round outcomes) with `node "<scripts>/task.js" note <id> --heading <h> --text "<...>"`, never with a heredoc or an Edit of the hand-off.
3. **Implement.** The context pack comes from `task.js start --role` (or `node "<scripts>/pack.js" <id> --role <role>` for another role). It writes `team/work/packs/<id>-<role>.md` (the brief, the spec and contract sections, threat entries and decisions the brief names) and prints the path and size. Then spawn the owner role from the board entry (for example `backend-developer`) as a one-shot subagent on the entry's model. Never pass a name. The prompt holds: one line on where the task fits, the pack path ("read this first; it is your requirements"), interfaces from earlier tasks, the resolved rules block, and the report it must return. Pass the pack path, not a list of files to read. The `pack-guard` hook refuses a developer, database-engineer, reviewer, security, test-engineer or final-reviewer dispatch whose prompt names no pack (g22); the owner-approved escape hatch is `--no-pack <reason>` in the prompt, recorded in the decisions log. `cost.js --save --task` warns when the task closed below 100% packed. Refs the pack could not find are listed under "Not found" in it: fix the brief or answer them in the prompt.
4. **Test gate.** Run `node "<scripts>/gate.js" --task <id>`. It runs every check of `gateCommands` in `team/config.json` (ordered `{name, command}` list, for example test, clippy, fmt; `testCommand` is the alias for a single check) and returns `ok`, `checks` (each with its own result), the exit code and the tail of the output; any red check fails the gate. With `--task`, `cargo test` and `cargo clippy` run only on the packages the task changed since its `chore(team): <id> start` commit and the packages that depend on them; `scope` in the result names them, or says `full` and why (a lock file or root manifest changed, no start commit). Use `--full` when you need the whole workspace; the milestone and phase end run `gate.js` without `--task` (g55). Shared role rule: a red check you see is recorded as a finding (`findings.js add`) even when it is outside your change; "not my change" is never a reason to stay silent. Known reds and reruns (g64): `cargo test` runs with `--no-fail-fast`; a test check red only on `gateKnownRed` tests (each with a recorded finding) counts as green and names them in `knownRed`, and `knownRedPassed` names a listed test that passes now: remove its entry and close its finding. Add an entry only for an environmental red with a finding, never for a red your change caused. A red check runs again before it counts (`gateRetry`); a check in `flaky` (red, then green) is not a round, but record the cause as a finding when it repeats. A failing gate is one round (step 6): send the output back to the implementer and never spawn a review on failing tests. One exception (g44): when the result says `fixable: true` (only format-type checks with a fix command are red), run `node "<scripts>/gate.js" --task <id> --fix` yourself. It runs the fixes, commits them as `style(<id>)` and runs the gate again; that is not a round and needs no dispatch. Add the style commit to the task's commits at close. A task marked `code: no` (board entry or brief; spikes, research, docs-only) has no tests: the same command then checks the report file named by the brief's `Output: <path>` line instead. It must exist, carry a verdict line (`Verdict: GO`, `Verdict: GO-WITH-CHANGES` or `Verdict: NO-GO`) and have an acceptance criteria section; `problems` lists what is missing and a failing check is a round like any failing gate. The planner sets the flag. If no `testCommand` is set, stop and ask the owner for it as an owner question. The result also has `skipped`: the count of skipped, ignored and todo tests the runner reported over the whole output. Runners hide the stdout of passing tests, so a test that prints "skip" and passes is not counted here: the review rule in `code-reviewer` and `test-engineer` catches that form.
5. **Review.** Only after the gate passes: `update <id> --status review`. Save the gate output to a file (`node "<scripts>/gate.js" --task <id> > team/work/packs/<id>-gate.json`), build the reviewer's pack with the diff: `node "<scripts>/pack.js" <id> --role code-reviewer --base <base-sha> --gate team/work/packs/<id>-gate.json`, and spawn `code-reviewer` as a one-shot subagent with only that pack path. It must give both a spec-compliance and a quality verdict. Record every verdict on the board as it comes: `board.js review <id> --role code-reviewer --verdict pass` for `APPROVED`, `--verdict fail` for `CHANGES_REQUESTED` (g59). `task.js close` refuses a task owned by a code role (backend-developer, frontend-developer, database-engineer, test-engineer) without a code-reviewer pass; a `code: no` task needs none.
6. **Fix rounds.** At most `reviewRoundCap` rounds (2 by default) per task: `board.js round` refuses the next one (see "Review round cap" below). The lead never fixes a role's output itself: every fix goes back to the owning role. `to-lead` means you decide, re-plan or escalate (architect, owner); it never means you implement. Once the decision exists, the implementation round goes to the task's owning role with a delta pack (`--paths` set to the task's code paths), carrying the decision id and any probe findings as notes. You edit only team files (board, briefs, decisions, hand-offs) and one-line text fixes in docs, never source or test code. The `rounds` field of the board entry is the only round count; notes and packs refer to it and keep no count of their own. Each failing gate, `CHANGES_REQUESTED` or failed attempt is one round: run `node "<scripts>/board.js" round <id> --reason <gate|review|stuck>` and act on `next.action` (skill `escalation`). Every fix round and every re-review uses the delta pack, never the full pack, for every role (developers and the test engineer, reviewers such as `code-reviewer`, `security-reviewer` and `final-reviewer`, and an architect folding findings into the spec): save the findings (or the gate output) to a file and run `node "<scripts>/pack.js" <id> --role <role> --round <n> --findings <file> --base <sha-of-previous-attempt>` (`--gate <file>` instead of `--findings` for a failing gate). It holds the findings, the diff since the previous attempt and the brief's acceptance criteria only; the role already has the brief and spec from its first pack. Re-dispatch the implementer with that pack path; run the gate again, then re-review with a delta pack of the same form. A criteria section the pack could not find is listed under "Not found": add it to the prompt. The diff in every pack leaves out `team/` (state, not code). Add `--paths <p1,p2>` with the task's code paths (from the brief) whenever you know them, so a base that spans `chore(team)` or docs commits still gives a code-only diff. A pack up to 25% over `packMaxChars` (60000 by default) is accepted automatically and `pack.js` prints a note. Above that it first leaves the diff of the changed test files out of the pack and lists them (`testsLeftOut`): name those test files in the prompt so the role reads them in the repository. Only a pack still over 125% is written with exit 3 and a warning on stderr: that is a stop, never dispatch it as is. Narrow it with `--paths` or a later `--base`, build it again, and use `--allow-large` only when the owner accepts the size.
7. **Hand-off.** When the reviewer says `APPROVED`, make sure `team/work/handoffs/<id>.md` exists (a read-only role sends it to you to save). When the gate reported `skipped` greater than 0, write the reason for each skip in that hand-off before `done`; a skip you cannot explain goes back as a fix round.
8. **Done.** A task tagged `security: contract` (it changes a security contract: new crypto, auth or permission model, threat-model mitigation) needs `security-reviewer` before done (pack with `--role security-reviewer`, then `board.js review <id> --role security-reviewer --verdict pass`); `board.js` refuses done without it. A `security: yes` task is reviewed per module (see "Hardening"). Put the task's deferred owner questions first: `node "<scripts>/decisions.js" flush --task <id>` prints them in groups of up to 4, one `AskUserQuestion` call per group (`board.js` refuses `done` until none is deferred). Then close the task in one call: `node "<scripts>/task.js" close <id> --commit <sha> [--findings <file>] --lead-note "<risks and what the next session must know>"`. Read `<sha>` from git first (`git log -1 --format=%h`, or the task's range); it is checked to exist and be reachable from HEAD, and the close is refused otherwise. Roles do the same before they put a commit hash in a report. `--findings` is a JSON file with the reviewers' non-blocking findings (an array of `{module, file, line, symbol?, severity, class, text, origin?}`; see "Findings and hardening"); a malformed one stops the close before anything is recorded, and the output lists each recorded finding with `hardeningDue`. The close sets `done` with the commit and the hand-off (the same refusals as `board.js update --status done`), writes `team/metrics/cost-<id>-<date>-<HHMM>.md` when the task has none (it warns, and still closes the task, if that fails), writes the lead hand-off when the rotation is due (see "Session rotation") and commits it all as `chore(team): <id> done`. For a code task it also writes `team/metrics/scope-<id>.json`: how many of the changed files the brief's `Files:` line names and the others by kind (lock, registration, fixture, test, other). It is a record, not a check. A `team/` file inside the task's code commits comes back as a warning: tell the role, do not rewrite history. Correct a wrong finding address with `findings.js amend <F-id> --file <f> --line <n>`, never by hand; `findings.js pack --module <m> --ids <F-1,F-2>` packs part of a module's findings. Retitle a board entry with `board.js update <id> --title <text>`. Ask `doc-writer` to update the project documents when the task changed behaviour.
9. **Commit the team state.** `team/work/` is committed (only `team/work/packs/` is ignored). `task.js start` and `close` commit it themselves; for anything else that changed there between tasks, commit what changed (board, briefs, hand-offs, escalations, mailbox, and `team/decisions.md` if it changed) as its own commit `chore(team): <what>` (for example `chore(team): T-004 done`). Commit with `node "<scripts>/team-commit.js" --message "chore(team): T-004 done"` (it runs `git commit -- team/`, a team/-only pathspec: explicit paths only; run team-commit.js on its own, never chained with `&&` or an inline `node -e`, so the project allow rule covers it (g27)), or by hand with `git add team/ && git commit -m "chore(team): ..." -- team/`; never a plain `git commit`, `git add -A` or `.`: the shared index may hold a developer's staged code, and a commit without the pathspec sweeps it in (D-227). Never mix these files into a code commit: the task's code commit is already made by the role before step 8.
   Measure the task first: `node "<scripts>/cost.js" --save --task <id>` writes `team/metrics/cost-<id>-<date>-<HHMM>.md` (that task only, lead included) and appends the rows to `team/metrics/cost.jsonl` (and one summary line to `~/.claude/nac/metrics.md`, on this machine only). Include those files in the same `chore(team)` commit. `team/metrics/` is committed, not ignored. To keep a reference for later comparison, `cost.js --baseline <name> [--session <id>] [--until <iso>]` writes `team/metrics/baseline-<name>.md`.

## Findings and hardening

Reviewers classify every finding by severity (`blocker`, `hardening`, `minor`) and class (`observed`, `known`, `theoretical`). Only a `blocker` goes back as a fix round. Everything else you record with `node "<scripts>/findings.js" add --module <m> --file <path> --line <n> [--symbol <name>] --severity <s> --class <c> --task <id> --text "<...>"`; a task with only non-blocking findings is done. A re-review checks only the listed findings and the lines the fix changed.

When `findings.js add` reports `hardeningDue` (the module has `findingsBatch` counted findings, 8 by default; only open `hardening` and `blocker` findings count: `minor` ones, items added with `--migrated` for a bulk import of old items, and items added with `--origin hardening` from a hardening task's review are kept but wait for the phase end), or at a milestone or phase end, ask the `planner` for one hardening task for that module. Build its pack with `node "<scripts>/findings.js" pack --module <m>` (the open findings, the lines around them, the impact sites and the tests that reference the symbol) and give developer and reviewers that pack only: nothing re-scans the whole module, the work and the review cover the pack items, what they affect and the diff. After each fix run `node "<scripts>/findings.js" close <F-id> --commit <sha>` (sha read from git). `security-reviewer` reviews a module once, at its hardening task and at milestone or phase end over the security-tagged changes since its last pass: `board.js review --module <m> --role security-reviewer --verdict pass` (tasks carry their module: `board.js add/update --module <m>`). `board.js phase` refuses while a blocker finding is open or a module lacks that pass.

Hardening loop. Add the task with `board.js add --module <m> --hardening yes`: at most one hardening task per module per phase; a second is refused unless the owner approved it and its decision is recorded (`--decision D-xxx`). A hardening task's review covers its changed lines and their direct impact sites only (the pack says so; no module re-scan). A `blocker` found there is fixed inside the same task and counts against its round cap; every other finding is recorded with `findings.js add --origin hardening` and waits for the phase end, so one hardening review never opens the next hardening task. The brief names the violated invariant (the property that must always hold, for example "no code path reads a database file the lock does not cover"), not only the probed route, and requires a test for every route to that invariant; a fix that closes only the route the probe found is the pattern this prevents.

## Decisions and checks

You never Edit `team/decisions.md` by hand. Record several outcomes in one call with `decisions.js record --file <json>`, fix a field with `decisions.js amend D-xxx --<field> <value>` and replace an earlier decision with `record --supersedes D-xxx` (also per item in the file). The lead does not run builds or tests itself: read the gate script result (step 4) or the developer's report summary line.

## Resuming a task

When you resume a task after a restart, quota stop or new session, read its hand-off first (`team/work/handoffs/<id>.md`) and `git log` for its commits, then dispatch only the remaining steps. A task without a size counts as M: `board.js update --status done` is refused on an M or L task with at most one code commit unless `--single-commit "<reason>"` is given (recorded in the decisions log). Mark a small task `--size S`; a task that produces no code is `--code no`.

A role the usage limit cut off (its task notification says `failed` with "hit your session limit" or `rate_limit`) is not stuck and not a round. Before you re-dispatch it, run `agent-state.js <agentId>` (the `<task-id>` of the notification). When it says `resume`, wait for the limit to reset and continue that same role with SendMessage to its agent id ("The usage limit has reset. Continue where you stopped."): it keeps what it read and did, and its turn count. When it says `fresh`, the role had barely started or is near its turn budget: re-dispatch with a fresh pack. Never `board.js round` for a limit stop (g63).

## Session rotation

The lead session grows with every task, and every call re-reads it. With compaction configured (`autoCompactWindow` in `.claude/settings.json`) the lead rotates after every task (g34); with `/clear` (an owner step each time) after every 5 tasks; `rotateEvery` in `team/config.json` overrides both. Rotate also at each milestone end (your own call). `task.js close` does steps 1 to 3 below itself when the rotation is due: it writes `team/work/handoffs/lead-<YYYY-MM-DD-HHMM>.md` from the board and the decisions log with your `--lead-note` in it, resets the counter and commits; its output says `rotate: true`, `rotateBy` and `leadHandoff`. So give every close a `--lead-note` with the facts the next session needs (risks, decisions in flight, what you were about to do). By hand (a milestone end, or `board.js update --status done` printing `rotate: true`):

1. Write `team/work/handoffs/lead-<YYYY-MM-DD-HHMM>.md`: done, in progress, next task, open questions, risks. Only facts the next session needs. Never write the question lists by hand: paste the output of `node "<scripts>/decisions.js" handoff-questions` (queued and parked, from the log), so a question a decision closed is not listed as open.
2. Run `node "<scripts>/board.js" rotated` to reset the counter.
3. Commit the hand-off and the board as `chore(team): lead hand-off <YYYY-MM-DD-HHMM>` with `node "<scripts>/team-commit.js" --message "<that message>"` (explicit paths only: a `git commit -- team/` pathspec, so staged developer code is never swept in).
4. Then, by `rotateBy`:
   - `compaction`: nothing for the owner to do. The hand-off is on disk; carry on with the next task and let autocompact run when the PreCompact hook allows it (it writes its own compact hand-off and the session resumes from it). Do not ask for `/clear`. The hook lets it run at a safe point; a missing task hand-off or uncommitted `team/` files defer it by `compaction.softMargin` tokens at most (20000 by default, g32), an open owner question up to the ceiling. An `autoCompactWindow` of 100000 (`setup.js --compaction --window 100000`, run by the owner) makes it come at about each task end.
   - `clear` (compaction is off): tell the owner to run `/clear`, then say "devam" (or "continue"). The session-start summary then shows the newest `lead-*.md` as "Lead hand-off"; read it first and carry on from the next task. Suggest `setup.js --compaction` once so the next rotation needs no owner step.

## Parallel tasks

Parallel code tasks always get their own worktree: `board.js update <id> --status in-progress` is refused while another code task is in progress in the same tree (two implementers share one git index, and a formatter or commit of one pulls in the other's files). When an implementer is already active and another task starts, the new task does not share the working tree. Run `node "<scripts>/worktree.js" add <id>`: it creates a git worktree at `<repo>-wt/<id>` on branch `task/<id>`, outside the repo (or under `worktreeRoot` in `team/config.json`, for a drive with space). Record it on the board: `board.js update <id> --status in-progress --worktree <printed path>`. Brief, pack, hand-off and board stay in the main project; the pack path is absolute, and the role works inside the worktree path. `pack.js --base` and `gate.js --task <id>` take the diff and run the checks in the worktree the board records, so run them from the main project without `--project <worktree>` (g28). Build output stays inside the worktree; when it must go elsewhere (a second profile, a separate target dir), use the `target` path `worktree.js add` prints (`target-<id>` beside the worktree, a suffix such as `target-<id>-sec` is fine), never a scratchpad or another drive. `worktree.js remove` deletes those with the worktree. When a drive is full, move `worktreeRoot` in `team/config.json` instead (g50).

After the reviewer says `APPROVED` and the gate is green, integrate locally: `node "<scripts>/worktree.js" integrate <id>` cherry-picks the task's commits onto the working branch (it aborts and leaves the branch unchanged on a conflict; then the task goes back as a fix round), then `worktree.js remove <id>` deletes the worktree and the branch. The owner decided that this local integration is part of the loop, so it needs no separate approval. It is a cherry-pick onto the working branch, not a push and not a merge of a remote or release branch: push, merge into the main branch, deploy and publish still need the owner's separate approval for that one action.

Every role stages only its own paths (`git add <path>`), never `git add -A` or `git add .`: another task's unstaged work must never ride along in a commit.

## Automation first

Before you or a role hands the owner a manual step, try the automated path: scripts, CLI, launching the program, capturing output to files. Hand the owner only what truly needs a human (keystrokes in a GUI or terminal, visual judgement, credentials), each as one exact minimal action (the one command to type, the one thing to look at and what to look for). Every role has this rule in its agent file.

## Role rule

Every role gets a pack and follows this rule, which its agent file repeats: "Start from the pack. Do not explore files the pack does not name; if you need more, read only that and say what and why in your report." Reviewers (`security-reviewer`, `final-reviewer`) get the same pack form with their own `--role`. Roles that work on a phase rather than a task (architect, planner, researchers, assistant) treat their assignment file as the pack; the research roles' file lives under `team/research/` so the research guard stays as it is.

## Turn budget

Every dispatch has a budget of `turnBudget` model turns (40 by default, from the resolved rules; parallel tool calls share a turn; the old name `callBudget` still works). The pack header states it; `maxTurns` is the budget plus 5 in the agent files, so a role that reaches the budget still has turns left to write its report before the hard stop. A role cannot count its own turns: the `turn-budget` hook counts them from its transcript, tells it in its last 5 turns to finish the step it is on and commit green work, and at the budget tells it to stop and report without committing (g36); a hook refuses `git commit` from a role at the budget (g61), and the next pack lists the uncommitted files. Keep `turnBudget` below `maxTurns`, or the notice comes after the hard stop. When a role reports that it hit the budget, you decide: re-dispatch with a fresh pack for the remainder (`pack.js` again, so it holds the current diff; this is the same round, not a new round, and `board.js round --reason budget` is refused, g46) or split the task into smaller board tasks. Never count a budget stop as `--reason stuck`: the hook records the stop and `board.js round --reason stuck` is refused until a fresh pack for that role (g60). You never raise the budget silently: a changed `turnBudget` is an owner decision, like any config change.

## Review round cap

A task gets at most `reviewRoundCap` rounds (2 by default, from the resolved rules), counted from its start or from its last approach decision. When a reviewer (`code-reviewer`, `security-reviewer`) or the test gate still returns findings after that, `board.js round <id>` refuses with an error: the task gets no further fix round. Then:

1. Send the open findings and the round history to the `architect` as one approach question: options, root causes, cost of each. The architect answers read-only.
2. Bring the architect's answer to the owner as one question (Source/Status/Impact, options, one recommendation).
3. Record the owner's decision (`decisions.js`) and continue with `node "<scripts>/board.js" round <id> --approach <decision-id>`. The round count continues; the round that carries `--approach` is the first of the next window, so the cap applies again after one more round.

A changed `reviewRoundCap` is an owner decision. Findings that a reviewer marks "same class as round <n>" are the pattern this rule exists for: another way past the same check means the approach, not the text, is wrong.

## Lessons

Record a lesson at the moment it happens, with `node "<scripts>/lessons.js" add --trigger <text> --what <text> --rule <text> [--task <id>]` (one line each: what set it off, what happened, the rule that would have prevented it). It appends to `team/lessons.md` and to `~/.claude/nac/lessons.md` (this machine only, never sent anywhere). Add one when: an escalation reaches `to-lead` or `to-owner` (skill `escalation`); a role repeats the same mistake in a task; the owner corrects the lead. A lesson is a proposal: nothing becomes a NAC rule unless the owner decides so at a phase report. Commit `team/lessons.md` with the next `chore(team)` commit.

## Never

- Never run two implementers on the same files at once.
- Never mark `done` without an approved review and a hand-off note (the `TaskCompleted` hook also checks this in team mode, when Claude Code offers native team task tools).
- Never let a role decide a product or design question; it comes to you as an owner question.
