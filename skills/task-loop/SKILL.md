# Task loop

Adapted from superpowers subagent-driven development (see NOTICE).

The board (`team/work/board.md`) is the source of truth. A task whose board status is `done` is never dispatched again, even if you do not remember finishing it. This file holds every rule in short; `reference.md` next to it (`<skills>/task-loop/reference.md`) has the full text, the reasons and the rare paths. Read its section when a step needs the detail.

## Never

- Never run two implementers on the same files at once.
- Never mark `done` without an approved review and a hand-off note (the `TaskCompleted` hook also checks this in team mode, when Claude Code offers native team task tools).
- Never let a role decide a product or design question; it comes to you as an owner question.
- Never fix a role's output yourself, never run builds or tests yourself, never Edit `team/decisions.md` by hand.

## Review round cap

A task gets at most `reviewRoundCap` rounds (2 by default), counted from its start or its last approach decision; then `board.js round <id>` refuses. Then: 1) send the open findings and the round history to the `architect` as one approach question (options, root causes, cost of each; read-only); 2) bring its answer to the owner as one question (Source/Status/Impact, options, one recommendation); 3) record the decision (`decisions.js`) and continue with `node "<scripts>/board.js" round <id> --approach <decision-id>` (the round count continues; that round is the first of the next window). A changed `reviewRoundCap` is an owner decision. Findings marked "same class as round <n>" mean the approach, not the text, is wrong.

## Turn budget

Every dispatch has a budget of `turnBudget` model turns (50 by default; parallel tool calls share a turn; the old name `callBudget` still works). The pack header states it; `maxTurns` is the budget plus 5 in the agent files, so a role at the budget still has turns to write its report. The `turn-budget` hook counts the turns, warns in the last 5, stops the role at the budget without committing (g36) and refuses its `git commit` (g61). When a role reports the budget hit, you decide: re-dispatch with a fresh pack for the remainder (the same round, not a new round; `board.js round --reason budget` is refused, g46) or split the task. Never count a budget stop as `--reason stuck` (refused until a fresh pack, g60). A changed `turnBudget` is an owner decision.

## Role rule

Every role gets a pack and follows this rule, which its agent file repeats: "Start from the pack. Do not explore files the pack does not name; if you need more, read only that and say what and why in your report." Reviewers get the same pack form with their own `--role`; phase roles (architect, planner, researchers, assistant) treat their assignment file as the pack.

## Automation first

Before you or a role hands the owner a manual step, try the automated path: scripts, CLI, launching the program, capturing output to files. Hand the owner only what truly needs a human (keystrokes in a GUI or terminal, visual judgement, credentials), each as one exact minimal action (the one command to type, the one thing to look at and what to look for). Every role has this rule in its agent file.

## For each board entry that is not `done`

1. **Brief.** The planner's brief names files, interfaces, exact values, the failing tests to write first and the commit message.
2. **Start.** `node "<scripts>/task.js" start <id> --role <owner-role>` (`--worktree` when another code task is in progress; `--paths <p1,p2>` for the pack). One call (g33): board `in-progress`, the hand-off skeleton `team/work/handoffs/<id>.md` with the base commit, the worktree, the pack, one `chore(team): <id> start` commit. Use the printed `base`; never write it from memory. A brief citing threat-model IDs tags the task `security: yes` (`securityNote`); set `contract` (`board.js update <id> --security contract`) when it changes a security contract. Add what the next session needs with `node "<scripts>/task.js" note <id> --heading <h> --text "<...>" --chore` (`--chore` commits team/ in the same call, g67), never with a heredoc or an Edit of the hand-off.
3. **Implement.** The pack (`team/work/packs/<id>-<role>.md`, or `pack.js <id> --role <role>` for another role) holds the brief, spec and contract sections, threat entries and decisions. Spawn the board entry's owner role as a one-shot subagent on the entry's model; never pass a name. Prompt: one line on where the task fits, the pack path ("read this first; it is your requirements"), interfaces from earlier tasks, the resolved rules block, the report it must return. Pass the pack path, not a file list; the `pack-guard` hook refuses a dispatch with no pack (g22; escape hatch `--no-pack <reason>`, recorded). Refs under "Not found": fix the brief or answer them in the prompt. `briefForbidden` (g79, from `briefForbid` in `team/config.json`): the brief names a way the project's rules refuse; if it tells the role to use it, fix the brief before you dispatch. Size L (g75): plan one step (one commit) per dispatch from the start, never the whole task in one dispatch; each dispatch ends on a green commit and the next pack carries its diff (`--base`). M stays one dispatch unless the brief has more than 3 steps.
4. **Test gate.** `node "<scripts>/gate.js" --task <id>` runs every `gateCommands` check (scoped to the changed packages and their dependents; `--full` for all; milestone and phase end run without `--task`, g55) and returns `ok`, `checks`, the tail and `skipped`. Run it in the foreground with the tool timeout at its maximum (600000 ms), never as a background shell: Claude Code stops a background shell under memory pressure while the session waits, and the gate result is lost (g71). On `splitRequired` (the checks took longer than `gateSplitSeconds`), run each returned `--check <name>` command in its own foreground call; green when every check is green; not a round (g104). Shared role rule: a red check you see is recorded as a finding (`findings.js add`) even when it is outside your change. Known reds and reruns (g64): `gateKnownRed` reds count as green (`knownRed`; remove an entry in `knownRedPassed`; add one only for an environmental red with a finding); a red check runs again first (`gateRetry`; a red `cargo test` reruns only its failed tests, one at a time, g69); `flaky` (red, then green) is not a round. A red result lists `failed` and `checks[].failures` (g65): put both in the round's brief. A red that is red on the task's base too (g66): record a finding and run `board.js round <id> --reason base --finding <F-id>` instead of a round; the same role fixes it on the same model. A failing gate is one round (step 6); never review on failing tests. When the result says `fixable: true`, run `node "<scripts>/gate.js" --task <id> --fix` yourself: it fixes, commits `style(<id>)` and reruns; not a round (g44). `code: no` tasks: the gate checks the brief's `Output:` report (verdict line, acceptance criteria). No `testCommand`: ask the owner. Detail: reference.md step 4.
5. **Review.** Only after the gate passes: `update <id> --status review`, save the gate output (`gate.js --task <id> > team/work/packs/<id>-gate.json`), `pack.js <id> --role code-reviewer --base <base-sha> --gate team/work/packs/<id>-gate.json`, spawn `code-reviewer` with only that pack path (spec-compliance and quality verdict). Record every verdict as it comes: `board.js review <id> --role code-reviewer --verdict pass` for `APPROVED`, `--verdict fail` for `CHANGES_REQUESTED` (g59); `task.js close` refuses a code-role task without a pass.
6. **Fix rounds.** At most `reviewRoundCap` rounds. The lead never fixes a role's output itself: every fix goes back to the owning role. `to-lead` means you decide, re-plan or escalate (architect, owner), never implement; the implementation round then goes to the owning role with a delta pack (`--paths` set to the task's code paths), carrying the decision id and any probe findings as notes. You edit only team files and one-line doc text fixes, never source or test code. The board's `rounds` field is the only round count. Each failing gate, `CHANGES_REQUESTED` or failed attempt: `node "<scripts>/board.js" round <id> --reason <gate|review|stuck>` and act on `next.action` (skill `escalation`). Every fix round and every re-review uses the delta pack, never the full pack, for every role (developers, test engineer, `code-reviewer`, `security-reviewer`, `final-reviewer`, an architect folding findings): `node "<scripts>/pack.js" <id> --role <role> --round <n> --findings <file> --base <sha-of-previous-attempt>` (`--gate <file>` for a failing gate), with `--paths <p1,p2>` whenever you know the task's code paths. Pack size: up to 125% of `packMaxChars` is accepted (test diffs left out are listed in `testsLeftOut`: name them in the prompt); over that, exit 3 is a stop: narrow with `--paths` or a later `--base`; `--allow-large` only when the owner accepts. Detail: reference.md step 6.
7. **Hand-off.** On `APPROVED`, make sure `team/work/handoffs/<id>.md` exists. A `skipped` above 0 needs the reason for each skip (`skippedTests` names them) in it before `done`; an unexplained skip is a fix round.
8. **Done.** `security: contract` needs a `security-reviewer` pass on the board first; `security: yes` is reviewed per module. Flush deferred questions first: `node "<scripts>/decisions.js" flush --task <id>` (groups of up to 4, one `AskUserQuestion` call per group). Then one call: `node "<scripts>/task.js" close <id> [--findings <file>] --lead-note "<risks and what the next session must know>"`. A main-tree task's code commits since its start commit are taken from git (`stepCommits`, g103); `--commit <sha[,sha...]>` adds others, read from git first (`git log -1 --format=%h`); roles do the same before a hash goes in a report. `--findings` is a JSON array of `{module, file, line, symbol?, severity, class, text, origin?}`. The close sets done, writes the cost file and the scope record, the lead hand-off when the rotation is due, and commits `chore(team): <id> done`. Fix a finding address with `findings.js amend`, retitle with `board.js update <id> --title`. Ask `doc-writer` when behaviour changed. Detail: reference.md step 8.
9. **Commit the team state.** `team/work/` is committed (only `packs/` is ignored); `task.js start`, `close`, `note --chore` and `decide --chore` commit it themselves. For anything else: `node "<scripts>/team-commit.js" --message "chore(team): <what>"` run on its own, never chained with `&&` or an inline `node -e` (g27), or `git add team/ && git commit -m "..." -- team/`; never a plain `git commit`, `git add -A` or `.` (D-227), never mixed into a code commit. Cost: `node "<scripts>/cost.js" --save --task <id>` (close does it when missing). Detail: reference.md step 9.

## Findings and hardening

Findings carry a severity (`blocker`, `hardening`, `minor`) and a class (`observed`, `known`, `theoretical`). Only a `blocker` goes back as a fix round; record the rest with `node "<scripts>/findings.js" add --module <m> --file <path> --line <n> [--symbol <name>] --severity <s> --class <c> --task <id> --text "<...>"`. A re-review checks only the listed findings and the changed lines. On `hardeningDue`, or at a milestone or phase end, ask the `planner` for one hardening task for that module (`board.js add --module <m> --hardening yes`; a second per phase needs a recorded owner decision) with the pack from `findings.js pack --module <m>`; close each fix with `findings.js close <F-id> --commit <sha>`. Its brief names the violated invariant and requires a test for every route to it. `security-reviewer` passes a module with `board.js review --module <m> --role security-reviewer --verdict pass`; `board.js phase` refuses while a blocker is open or a module lacks that pass. Detail: reference.md "Findings and hardening".

## Decisions and checks

Record outcomes with `decisions.js record` (`--file <json>` for several), fix a field with `decisions.js amend D-xxx`, replace with `record --supersedes D-xxx`; `decide <Q> --chore` commits team/ in the same call. Read the gate result or the developer's summary line, never run builds or tests yourself.

## Resuming a task

After a restart, quota stop or new session, read its hand-off first (`team/work/handoffs/<id>.md`) and `git log` for its commits, then dispatch only the remaining steps. A task without a size counts as M: done is refused on M or L with at most one code commit unless `--single-commit "<reason>"`. A role cut off by the usage limit is not stuck and not a round (g63): run `agent-state.js <agentId>`; `resume` means SendMessage to its agent id after the reset ("The usage limit has reset. Continue where you stopped."), `fresh` means a fresh pack.

## Session rotation

With compaction (`autoCompactWindow`) the lead rotates after every task (g34); with `/clear` every 5 tasks; `rotateEvery` overrides, and `rotateBy` in `team/config.json` picks the way (g76: `clear` starts the next task at ~37k, a compaction at ~62k). `task.js close` writes the lead hand-off itself when the rotation is due (`rotate: true`, `rotateBy`, `leadHandoff`), so give every close a `--lead-note`. By hand (milestone end): the lead hand-off with the output of `decisions.js handoff-questions` (never hand-written lists), `board.js rotated`, `team-commit.js`. `compaction`: carry on, do not ask for `/clear`. `clear`: tell the owner (and the owner proxy) to run `/clear`, then "devam"; wait, and if "devam" comes without `/clear`, carry on in this session (`task.js start` refuses once after such a close, g80; run it again with `--same-session`). Detail: reference.md "Session rotation".

## Parallel tasks

Parallel code tasks always get their own worktree: `node "<scripts>/worktree.js" add <id>`, then `board.js update <id> --status in-progress --worktree <printed path>`. Run `pack.js --base` and `gate.js --task <id>` from the main project without `--project <worktree>` (g28). Build output stays in the worktree or the printed `target` path, never a scratchpad (g50). After `APPROVED` and a green gate: `worktree.js integrate <id>` (local cherry-pick, owner-approved part of the loop; a conflict is a fix round), then `worktree.js remove <id>`. Push, merge into the main branch, deploy and publish still need the owner. Every role stages only its own paths, never `git add -A` or `git add .`. Detail: reference.md "Parallel tasks".

## Lessons

Record a lesson when it happens: `node "<scripts>/lessons.js" add --trigger <text> --what <text> --rule <text> [--task <id>]`, when an escalation reaches `to-lead` or `to-owner`, a role repeats a mistake, or the owner corrects the lead. A lesson is a proposal until the owner decides at a phase report.
